现有结构能减少开发量，但不能给出“已完成 80%”之类的可靠比例。游戏资源尚未验证，且目前存在会跨页面传播的数据错误。

### 现有数据链路

首页从 `site.config.ts` 经 `config/content.ts` 适配后进入组件；子页从 `gameLibrary` 直接取数据并局部拼接。两条链路格式不同，是当前问题的重要来源。

建议建立一个明确的游戏数据模型与统一适配函数，供首页、子页、推荐、元数据、Sitemap 共用。主游戏通过 `mainGameSlug` 指向游戏库，避免同一游戏在两个文件中维护两套内容。

| 体验优先 | 没有 Reload、保存提示、加载异常引导和紧邻播放器的 Controls | 不能满足原报告播放器要求 | 增加对应组件，避免把 iframe onload 当作可玩信号 |

| 体验优先 | 首页只设置 canonical；根布局自行拼 title | 配置中的 `mainGame.seo.title` 没有真正驱动首页标题 | 首页显式输出主游戏 SEO，子页输出自己的 OG/Twitter |

Cloudflare 当前文档给出的静态资源单文件上限为 **25 MiB**，因此旧资源清理是部署可行性的实际问题，不只是体积优化。[Cloudflare 平台限制](https://developers.cloudflare.com/workers/platform/limits/)

另外，`app/schema.ts` 定义了指向 `/search` 的 SearchAction，但仓库没有对应搜索路由。该定义目前不等于已经输出到所有页面；后续不要直接复用不存在的功能声明，也不要启用没有真实数据的评分 Schema。

## 四 技术方案与部署路径

### 推荐保留 Next.js 并静态导出

Next.js 支持通过 `output: 'export'` 生成 `out/` 静态文件；动态路由需要预先枚举，运行时 rewrites 不属于静态导出能力。Client Component 也可以预渲染为 HTML，不能仅凭 `use client` 判定 SEO 文本不存在。[Next.js 静态导出文档](https://nextjs.org/docs/app/guides/static-exports)

本项目没有必须依赖请求时服务器逻辑的业务：游戏在第三方 iframe 运行，正文和推荐在构建时已知，联系入口只是邮箱。因此，静态导出与现有需求匹配。

| 方案 | 复用程度 | 新增工作 | 判断 |
|---|---|---|---|
| Next.js 静态导出 + Cloudflare 静态资源 | 高 | 修复模板、导出和静态路由 | 首选，延续原报告的 Cloudflare 方向 |
| Next.js 常规部署 | 高 | 仍需修复模板和依赖，增加运行环境核验 | 若用户已有成熟平台，可作为备选 |
| 重写 Astro | 需要迁移 React 页面与配置链路 | 新建组件、路由和验收链路 | 当前缺乏足以抵消迁移工作的收益 |

保留 Next.js 不等于保留老版本。官方支持页面已将 Next.js 13.x 列为不支持版本，当前页面列出 16.x 为 Active LTS。正式上线前应迁移到当时仍受支持、已打安全补丁的稳定版本，并联动检查 React、构建工具和 Node 要求。[Next.js 支持策略](https://nextjs.org/support-policy)

升级时尤其检查 `[slug]` 的参数类型、Metadata API、Lint 命令和组件依赖，不能只更新 package.json 数字。先记录旧版基线，再完成升级与回归；无需为保留框架强行保留全部历史依赖。

### 目标构建与发布流程

1. 在游戏配置中完成发布校验，拒绝空 iframe、占位游戏、重复 slug 和缺失 SEO。
2. 首页从 `mainGameSlug` 读取数据；静态子页只枚举发布集合中的其他游戏。
3. 使用 `output: 'export'`，统一尾斜杠规则，禁止未枚举动态路径。
4. 不再依赖旧 `.embed` rewrite，播放器直接使用经过验证的嵌入地址。
5. 字体优先采用系统字体或可合法分发的本地字体，避免构建必须访问 Google Fonts。
6. 从同一份发布集合生成 Sitemap、robots 和元数据。可使用 Next Metadata Routes，但必须验证最终文件确实进入 `out/`；不维护两套相互冲突的生成器。
7. 导出后扫描 `out/`：链接、HTML 主体、资源大小、旧域名、占位词、404 文件、Sitemap 和 robots。
8. Cloudflare 只上传经过检查的 `out/`，不直接上传仓库或 `.next/`。

建议统一采用带尾斜杠的游戏 URL，与原报告保持一致。Cloudflare 配置使用 `assets.directory` 指向 `./out/`，`not_found_handling` 使用 `404-page`，HTML 路由规则与导出目录一致。未知地址返回 404，不配置首页 SPA 兜底。[Cloudflare SSG 与 404](https://developers.cloudflare.com/workers/static-assets/routing/static-site-generation/)

测试环境使用 `noindex`，并优先通过访问控制隔离。不能仅用 robots.txt 禁止抓取来代替防索引；正式环境再切换真实域名、自引用 canonical 与允许索引的配置。正式构建在生产域名缺失时应报错，而不是回退到旧域名或虚构域名。

| 状态 | 定义 | 是否发布 |
|---|---|---|
| PASS | 在声明支持的设备上完成加载、进入战斗和实际操作测试 | 可以进入候选发布集合，仍需内容与来源检查 |
| UNVERIFIED | 有线索或项目地址，但实测不完整 | 不发布 |
| BLOCKED | 证实无法嵌入、加载或操作 | 不发布，记录原因 |
| REJECTED | 玩法与页面意图不符，或体验不达标 | 不发布 |

桌面和移动端分别记录 `PASS / FAIL / UNVERIFIED`。桌面通过、触屏不支持的游戏可以考虑桌面限定发布，但页面和卡片必须明确标注 Keyboard required，不能宣传为手机可玩。仅页面响应式适配不算触屏通过。

正式测试应在本地或测试域名的父页面中嵌入，而不只是直接打开 iframe URL。至少验证首次加载、菜单、实际战斗、按键焦点、重新加载、全屏进入退出、音频首次交互和移动端横竖屏。HTTP 200 和 iframe onload 都不算战斗验证通过。

## 六 页面体验与数据改造

### 页面结构

首页和子页使用相同顺序：Header → 独立 H1 与简短介绍 → 游戏播放器 → Reload 与 Fullscreen → Controls 与设备说明 → Related Games → How to Play → About this Game 与作者来源 → 可选 Features → FAQ → Footer。

沿用现有容器和卡片布局，减少当前 `mb-16`、`mb-24` 带来的大段空白，保证玩家尽早看到游戏与操作说明。深色背景、清晰边框和少量紫色或红色强调即可，不需要动态背景或首屏大幅展示图。

移动端优先保证画面完整、操作可达和页面不横向溢出。不要用固定 16:9 套所有游戏；舞台与播放器控制栏应共同纳入高度计算。TurboWarp 文档说明其默认舞台与控制栏存在额外尺寸，最终仍以具体嵌入版本实测为准。[TurboWarp 播放器尺寸](https://docs.turbowarp.org/embedding)

### 播放器行为

- Reload 仅重建或重新加载当前 iframe；按钮明确提醒未导出的进度可能丢失，不声称能保留存档。
- Fullscreen 监听真实全屏状态；处理不支持、用户拒绝和 Esc 退出。手机不支持时提供诚实的横屏提示。
- 每页只挂载一个游戏 iframe。相关推荐只显示图片和站内链接，不后台加载其他游戏。
- 不能跨域读取游戏内部 DOM 或可靠推断其“已经开始”。加载提示只能反映父页能够确认的状态。
- 游戏失败时提供重试、已知问题与原项目入口。作者来源链接可以外跳；推荐卡片必须留在本站。
- 不新增虚拟手机按键作为通用解决方案，除非游戏提供可验证的输入接口。

### 游戏配置建议

| 字段组 | 内容 |
|---|---|
| 身份 | `slug`、`name`、`series`、`author`、`sourceUrl` |
| 发布 | `published`、`verification.status`、`testedAt`、`evidence` |
| 播放 | `iframeSrc`、播放器比例或高度策略、重载提示 |
| 设备 | desktop、mobile、fullscreen 分项结果及限制 |
| 内容 | shortDescription、controls、howToPlay、about、features、faq |
| 搜索与分享 | title、description、封面、OG 图；canonical 由站点 URL 和路由生成 |
| 推荐 | `relatedSlugs`，统一过滤当前游戏与未发布游戏 |

推荐、Footer、Sitemap 和 `[slug]` 不得各自维护一套名单。构建阶段发现无效发布记录应直接失败，避免静默生成残缺页面。

### 当前竞争格局

`deltarunesim.com` 自述拥有 300 多个战斗、Boss Rush、练习与回放功能，以及独立 Boss 页面。这些是其页面公开声明，本次未逐项游玩核验；但足以说明它在内容深度上构成竞争。[DELTARUNE Fight Simulator 首页](https://deltarunesim.com/)

`badtimesimulator.io`、`sansfight.net` 保留为 Sans 专项研究候选，本次没有对它们完成最新实测或排名核实。

V4 版本号本身不构成壁垒。可验证的差异应来自：更顺畅的启动、准确的按键与保存说明、明确的设备兼容、可用的游戏筛选，以及能解决玩家问题的原创测试内容。是否真正优于竞品，要由对照测试决定。

### 页面 SEO 规则

首页仅承接 `deltarune fight simulator`；每个子页承接对应游戏意图，不用同一个 iframe 批量创建近义词页面。

每页至少具备独立 title、description、正文 H1、自引用 canonical、正确分享图、真实操作说明、设备限制和来源。首页标题可暂拟为 `Deltarune Fight Simulator — Play Battle Simulator V4`，但功能性描述须在游戏验证后定稿。

首批页面数量少，不做分类页、分页或攻略博客。保留 About、Contact、Privacy、Terms，它们用于解释站点身份和真实数据处理方式，不用作凑词数的内容页。

FAQ 应解决启动、按键、保存、全屏、设备支持等真实问题。验收时检查初始 HTML 中是否包含重要答案；当前 Accordion 关闭状态下的输出需实测，必要时改为能保留正文的实现。没有搜索结果特殊展示保证，也不为此添加不存在的评分或功能。

目前 robots 配置允许一般搜索引擎，却限制多个 AI 抓取代理只访问 llms 文件。这是渠道选择，不应笼统称为“AI SEO 优化”。先明确各渠道意图，再决定规则；旧 `public/llms.txt` 要同步更新或从新站产物中去掉。

## 八 商业可行性与投入控制

### 运行成本

Cloudflare 文档说明静态资源请求免费且不设请求数量上限，Assets 存储不另收费；调用 Worker 脚本则适用 Workers 计费。对本项目而言，纯静态路线有利于控制托管成本。[Cloudflare 静态资源计费](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/)

这不等于项目总成本为零。仍有域名注册续费、开发验收时间、游戏可用性维护，以及可选分析或邮件服务成本。域名尚未确认，暂不报精确预算；首版没有必要增加数据库、R2、付费关键词工具订阅或常驻服务器。

### 广告收入不能从搜索量直接推导

应使用“实际站内页面浏览量 ÷ 1,000 × 实际 Page RPM”估算广告收入。关键词搜索量需要经过排名、点击率、会话与浏览深度才能转为页面浏览量；游戏时长也不会自动变成额外 PV。

纯计算示例：假设 Page RPM 为 5 美元，月 PV 为 1,000、10,000、50,000，对应收入分别为 5、50、250 美元。**这里的 RPM 和 PV 都是演示假设，不是行业基准或项目预测**；广告未获批准时，该收入模型不成立。

原报告将 AdSense 风险主要写成“未经许可嵌入”。更准确的表述是：Google 对缺乏额外评论、筛选或其他价值的复制及嵌入内容设有限制，同时要求遵守知识产权政策。仅能嵌入、注明作者或增加数篇泛化文字，都不能保证审核通过。[Google 复制内容政策](https://support.google.com/publisherpolicies/answer/11190248?hl=en)

本项目应通过实测操作说明、设备兼容记录、失败排查和有依据的游戏推荐增加价值，并核查各游戏的来源与使用条件。不要沿用模板中“我们开发这些游戏”“官方网站”等不符合事实的身份描述。首版不必提前接广告脚本，接入广告与分析时再核实适用的隐私披露和同意要求。

### 继续投入的判断标准

| 情况 | 建议 |
|---|---|
| V4 无法稳定开始战斗 | 暂停完整网站开发，先解决来源或产品选择 |
| V4 可玩，其他游戏不足两款 | 单独评估缩小为单游戏验证版，禁止补空页 |
| V4 与至少两款子游戏通过，模板能够导出 | 进入首版实现与测试部署 |
| 上线后有收录、有相关曝光、出现有效点击 | 优先完善已有页，再扩展通过验证的游戏 |
| 没有收录 | 排查可抓取性、canonical、HTTP 状态与内容，不能直接判断没有需求 |
| 有曝光但点击弱 | 检查搜索意图、排名、标题与内容匹配 |
| 有流量但玩家频繁遇到加载失败 | 优先修复游戏可用性，停止新增页面 |
| 广告资格或收入不成立 | 重新评估维护成本，不把持续加页当作解决办法 |

### P2 与 P3 上线条件

正式上线需确定真实域名、联系邮箱及账号权限，并得到明确的发布指令。绑定域名后再次检查 canonical、OG URL、Sitemap 和索引设置。Search Console 提交必须以实际账户结果为准。

### P4 上线后观察

建议在第 7、14、30 天人工复核游戏可用性、收录、曝光、点击及相关推荐点击，第 60～90 天再评估增长方向。此处为运营计划，未创建任何自动监控任务。

父页面可以记录推荐点击、Reload、Fullscreen 请求等事件；跨域 iframe 没有可靠接口时，不记录虚构的 `game_started` 或 `battle_completed`。第三方播放器自身的行为数据不能假定能被本站获取。
